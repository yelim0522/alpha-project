# 2일차 완료: 준비용 KV 메모리 예약

2026-09-27 · `reserved-v1` 구현 및 소규모 정확성 검증. **최종 성능 비교 결과는 아님.**

## 바뀐 점

기존 검사는 지금 만들어진 KV만 세어서, 여러 준비가 동시에 시작하면 나중에 메모리가 부족해질 수 있었음. 새 모드는 **앞으로 만들 prefix와 늘어날 suffix까지 예약한 뒤 시작**함.

- Pallas 근사·핵심 조율형·후보 복제에 같은 예약 관리자 적용
- 공간 부족 시 새 준비 보류. 조율형의 시작 계획은 유지
- 예측 지연·토큰 증가에 맞춰 예약 확대. 확대 불가 시 추가 쓰기 전에 해당 준비 취소
- 전환·취소·세션 재진입·복제본 정리·정착 완료 때 반환
- prefix만 완료했을 때는 예약 유지. 실험 종료의 미완료 상태는 기록 후 정리
- 실제 생성한 양만 취소 낭비로 계산. 미사용 예약량은 별도 지표
- `run.py --memory-mode reserved`의 기본 조율형은 **detour를 끈 `coordinated-core-v1`**

예산은 **선제 준비용 KV 공간**만 의미함. 모델 가중치·기존 세션의 상주 KV·반응형 복구를 포함한 물리 GPU 전체 용량 보장은 아님. 전환 시 예약 반환은 준비 풀에서 서빙 상태로 넘긴다는 의미이며 KV 삭제를 뜻하지 않음.

## 구현과 실행 순서

`sim/memory.py`에서 공통 승인·확대·반환과 지표를 관리하고, `policies.py`에서 시작 요청을 제출함. `environment.py`의 자원 진행 전후 검사, `run.py`와 `minisim.py`의 전환·세션·종료 처리에 연결함. 예약 모드의 활성 정착 준비도 GPU 점유 계획에 포함함.

전환/세션 정리 → 정책의 계획·취소·시작 요청 제출 → 해당 주기의 실제 생성량 확인 → **반환 → 기존 준비 확대 → 새 준비 승인 → GPU·링크 진행** 순으로 동작함. 요청 제출은 실제 준비 생성이 아님. 정책별 대화 시계에서는 실제 생성량을 알기 위해 생성 진행 후, 목적지에 쓰기 전에 승인함. prefix 크기는 요청 당시 문맥으로 고정해 해당 주기 생성분과 구분함.

계획기의 점유 추정에는 같은 주기에서 나중에 메모리 부족으로 취소될 준비가 포함될 수 있음. 이번 작업은 메모리 안전장치이며 계획 전면 재최적화는 하지 않음.

동시 확대/시작 각각은 `(예측 전환 시각, 사용자 ID, 준비 epoch, 목표 서버)` 순. suffix를 전송하거나 나중에 복구하는 경우 모두 동일한 보수적 예약식 사용. 실제 생성량이 예상보다 크면 신규 승인 때도 그 양을 포함함.

## 검증 결과

자동 테스트 **57개 통과**: 기존 31개 + 예약 관련 26개.

검사 범위: 동시 승인, 예산 0/일치/초과, 데드라인 연장, 실제 생성량 급증, 두 suffix 모드, prefix 완료 후 유지, 보류 계획 유지, 중복 반환, 생성 실패 롤백, 목표 변경·예측 소멸, 세션 재진입, 원래 서버 복귀, 복제본 취소·승격, 정착 완료, 종료 정리, 두 대화 시계와 소규모 실행기.

작은 시나리오 **24회** 실행: 32명 × 120초, 4조건 × 3정책 × 2시드. Pallas 근사·핵심 조율형·헤징을 같은 준비 예산으로 검사. 복수 후보는 마지막 잡음 조건에서 활성화.

|---|---:|---:|---:|---:|
| 공통 시각·기본 | 6,000 MB | 5,987.91 MB | 113 | 0 |
| 공통 시각·작은 예산 | 600 MB | 595.05 MB | 2,381 | 0 |
| 정책별 대화 시각·작은 예산 | 600 MB | 598.96 MB | 1,957 | 0 |

- 승인 **2,479건**, 정리 후 반환 **2,479건**
- 용량/소유자 검사 **28,848회**, 위반 **0건**
- 보류 **6,599회**, 연속 보류 요청 구간 **2,458개**
- 확대 실패 **4건**은 쓰기 전에 준비 취소. 정상 원본 세션은 유지
- 기존 모드 회귀: 두 대화 시계 × 네 정책의 작은 시나리오 8개에서 수정 전후 모든 요약 지표가 정확히 일치

새 원자료: [`sim/memory_validation_v1.json`](../sim/memory_validation_v1.json). 개별 설정·시드별 지표·시작 시각 표본·코드 SHA-256 포함. 전체 승인/보류 이벤트는 실행 중 `policy.memory.events`에서 확인 가능.

### 지표 해석

- `memory_peak_reserved_target_mb` / `memory_peak_actual_target_mb`: 한 서버에서 관측한 예약/실사용 첨두
- `memory_unused_reserved_mb_s`: 자원 진행 직후의 미사용 예약량 × 제어 간격 합계. 연속시간의 정확한 적분이 아닌 이산 근사
- `memory_defer_attempts`: 보류 시도 수. `memory_deferred_requests`: 같은 사용자·세션·목표·복사 여부로 연속 요청한 보류 구간 수. 철회 후 재요청은 새 구간
- `memory_start_lag_mean_s`: 실제 시작 − 그 요청의 계획 시각. 격자상 조기 시작이면 음수 가능. Pallas는 창을 다시 고르므로 최초 보류부터의 총 대기 시간과 다름
- `memory_end_pending` / `memory_end_reserved_mb` / `memory_end_actual_mb`: 종료 정리 **전** 미완료 상태. 성공이나 낭비로 재분류하지 않음

## 재실행

저장소 루트 기준:

```bash
python3 -m unittest discover -s sim -p 'test_*.py'
python3 sim/validate_memory.py
python3 sim/run.py --memory-mode reserved --users 32 --steps 240 --vram-mb 600
```

검증 스크립트는 `sim/memory_validation_v1.json`만 재생성함. 기존 결과·그림·CSV는 변경하지 않음. 기본 `run.py` 및 기존 실험 스크립트는 여전히 `legacy` 모드임.

## 남은 작업

**3일차:** 잔여 복구 조건을 맞춘 Pallas, 단순 조기 시작 통제, 구성 요소별 비교군 구현. 공통 예약 규칙은 전 비교군에 동일 적용.

**그 이후:** 주요 성능 실험·메모리 민감도·동일 조건 소규모 최적해 비교. 기존 ‘7–8% 격차’는 계속 보류. 이번 24회로 새 개선율을 확정하지 않음.

TurnBoundary의 `BoundaryJob`에는 아직 예약을 연결하지 않았으므로 새 모드에서 명시적으로 거절함. `--memory-mode reserved --alternatives`도 오류로 중단함. 과거 84회 턴 경계 결과는 예약 전 버전으로 유지. 현재 코드로 과거 그림을 재생성하면 원본 코드 해시 검사가 중단시키므로, 과거 스냅샷에서 재현하거나 새 결과로 별도 그림을 만들어야 함.

# 1일차 결정: 조율형 알고리즘 v1의 범위

2026-09-27 · 상태: **1일차 설계 확정 → 2일차 예약 구현·소규모 검증 완료**

기존 코드의 동작과 한계는 [구현 감사 명세](coordination_algorithm.md)에 기록되어 있다. 아래는 1일차 구현 기준이며, 새 예약 모드의 구현·검증 현황은 [2일차 보고서](memory_reservation_validation.md)를 따른다. 예약 구현을 마쳤지만 최종 성능 재실험은 아직 진행하지 않았다.

## 1. 연구 질문과 핵심 방식

**이동 예측으로 같은 MEC 서버를 향하는 여러 사용자의 준비 시작 시점을 함께 계획하면, 독립적으로 준비할 때보다 자원 경합과 중단 시간을 줄일 수 있는가?**

제안의 명칭은 ‘자원 점유를 고려한 선제 KV 준비 시점 조율’로 사용한다. 알고리즘 계열은 **예측 전환 시각 순 탐욕 계획**으로 고정한다. 전환 전에 반드시 완료해야 한다는 제약은 두지 않고, 미완료 작업을 잔여 복구 비용으로 평가한다.

| 구분 | 결정 |
|---|---|
| 핵심 제안 | 준비 시작 시점 공동 선택, 예상 GPU 점유, 외부효과 대용치, suffix 처리 선택, EDF prefill 실행 |
| 모든 비교군의 공통 기반 | 준비용 메모리 예약·승인·반환 규칙과 동일한 자원 파라미터 |
| 보조 기능 | 예측 실패·핑퐁 시 기존 서버에서 답변을 전달하고 나중에 정착하는 detour/settle |
| 이번 주 확장 범위 밖 | Reactive/Pallas/Coordinated 자동 선택, 새로운 목표 서버 선택 알고리즘, 정확한 시간별 백홀 예약, 전체 GPU 메모리 관리 |

주 실험의 조율형은 **detour를 끈 핵심 방식**으로 한다. detour를 켠 확장은 예측 잡음 실험에서 별도로 비교한다. 현재 기본 `Coordinated()`는 detour가 켜져 있으므로, 그 이름만으로 새 핵심 방식을 실행했다고 해석하지 않는다. 구현 시 별도 버전·설정으로 구분한다.

## 2. 메모리 제약: 예약 후 준비 시작

### 제약 대상

서버별 예산 V는 **새 서버에서 선제 준비에 사용할 수 있는 KV 메모리 공간**이다. 모델 가중치, 기존 세션의 상주 KV, 실행 중 임시 버퍼, 반응형 복구의 전체 메모리를 포함한 물리 GPU 용량이 아니다. 기존 6 GB 설정도 이 준비용 예산의 의미를 유지한다. 내부 계산 단위는 기존 `kv_mb_per_token`과 `vram_budget_mb`에 맞추며 이번 변경에서 바이트 환산 규칙을 바꾸지 않는다.

서버 m에서 준비 j의 실제 점유를 Aⱼ, 예약량을 Rⱼ라 하면, 구현 후 매 자원 진행 전후에 다음을 만족해야 한다.

`0 ≤ Aⱼ ≤ Rⱼ`, `Σ Rⱼ ≤ Vₘ`

예약량에는 이미 생성된 상태가 포함된다. `실제 사용량 + 예약량`으로 이중 계산하지 않는다. 예약은 시작 승인 즉시 반영하므로, 아직 prefix가 만들어지지 않은 작업도 다음 승인에서 공간을 차지한다.

### 시작 예약량

준비를 실제로 시작하는 시각 s에서 다음과 같이 예약한다.

`R_start = c × [L_start + r_d × (max(예측 전환 시각 − s, 0) + Δt)]`

- `c`: 실험에 설정된 토큰당 KV 크기
- `L_start`: **실제 시작 시점**의 문맥 토큰 수
- `r_d`: 설정된 기본 생성 속도
- `Δt`: 한 번의 제어 주기. 다음 검사까지 늘어날 상태를 위한 여유

완성 예정 prefix 전량과 전환까지 증가할 suffix를 예약한다. suffix를 나중에 복구하는 모드에도 같은 식을 적용한다. 이는 복원할 전체 문맥을 수용하기 위한 보수적인 승인 규칙이다. 지연 복구 모드의 실제 준비 중 점유보다 많이 예약할 수 있으며, 예약 과잉과 승인 보류를 함께 보고한다. 이를 최적 메모리 배분으로 주장하지 않는다.

6 GB 준비 공간에서 두 작업이 각각 4 GB를 예약해야 한다면 첫 작업 승인 직후 예약 합계가 4 GB가 되므로, 두 번째 작업은 보류된다. 실제 생성량이 아직 0이어도 같은 원칙을 적용한다.

### 실행 중 증가·예측 변경

예측 시각만으로 실제 증가량의 상한을 보장할 수 없으므로 매 자원 진행 전에 다시 검사한다.

`R_forecast = c × [L_prefix + S_generated + r_d × (max(deadline − t, 0) + Δt)]`

`R_next = max(R_current, R_forecast, c × [L_prefix + S_generated + G_step])`

- `L_prefix`: 시작 때 고정된 prefix 전체 크기
- `S_generated`: 준비 시작 이후 현재까지 생성된 suffix 토큰 수(전송 여부와 무관)
- `G_step`: 이번 자원 진행에서 실제로 추가될 토큰 수
- 예측 시각이 앞당겨져도 실행 중 예약은 줄이지 않음. 반환은 작업 종료 시 수행

늘어난 예약량이 예산 안이면 추가 예약 후 진행한다. 공간이 부족하면 **해당 준비를 자원이 더 할당되기 전에 취소**하고, 실제 만들어진 준비만 낭비로 집계한 뒤 예약을 반환한다. 원본 세션과 정상 토큰 생성은 보존하며, 다음 주기 준비와 실제 전환 때의 복구는 정책의 기존 규칙을 따른다. 예약되지 않은 증가량을 먼저 만들고 나중에 초과를 기록하는 방식은 허용하지 않는다.

즉, 강제하는 것은 준비용 메모리 상한이며, 모든 사용자의 준비 성공·전환 전 완료까지 보장하지는 않는다. 취소·보류에 따른 지연 손실도 결과에 포함한다.

## 3. 예약의 생명주기와 공통 승인 순서

예약 소유자는 `(사용자, 세션, 준비 epoch, 목표 서버)`로 식별한다. 목표별 복제본은 각각 별도 소유자다. 사용자 ID가 영역 재진입 후 재사용되더라도 이전 예약을 이어받지 않는다.

| 사건 | 동작 |
|---|---|
| 시작 시각만 계획한 상태 | 아직 메모리를 예약하지 않음. 시작 승인 때 현재 문맥으로 재계산 |
| 시작할 준비가 예산에 들어옴 | 예약을 먼저 등록한 뒤 준비 객체 생성. 생성 실패 시 예약 롤백 |
| 새 준비가 예산에 들어오지 않음 | 시작 보류. 다른 이미 승인된 작업을 밀어내지 않음 |
| 한 작업의 요청량이 서버 전체 예산보다 큼 | 시작 불가 사유 기록, 상태·예측이 바뀌면 재평가. 전환 때 기존 복구 규칙 적용 |
| prefix만 완료 | suffix·전환 대기를 위해 예약 유지 |
| 전환 지연 또는 토큰 증가로 예약 확대 필요 | 위 증가 규칙으로 검사, 부족하면 해당 준비 취소·반환 |
| 준비 목표 변경·예측 소멸 | 기존 정책의 취소 규칙에 따라 준비와 예약 정리 |
| 실제 전환으로 준비가 소비됨 | 실제 준비 상태를 서빙 상태로 넘길 때 예약 반환. 예약 반환이 물리 KV 삭제라는 뜻은 아님 |
| 준비 취소·원래 서버 복귀·세션 재생성 | 해당 준비 예약 전액 반환. 미생성 예약분은 낭비로 계산하지 않음 |
| 정착용 배경 준비 완료·취소 | 일반 준비와 같은 예약 규칙 사용. 핵심 실험에서는 비활성 |
| 실험 종료 | 미완료 점유·예약을 먼저 기록한 뒤 반환. 미완료를 성공으로 처리하지 않음 |

반환은 중복 호출되어도 두 번 차감하지 않도록 처리한다. 수명주기 종료 후 예약이 남거나 준비가 존재하는데 예약이 없는 상태는 검사 실패다.

공통 처리 순서는 다음으로 고정한다.

1. 실제 전환·취소·세션 변경에 따른 반환
2. 살아 있는 준비의 추가 예약 검사
3. 이번 주기에 시작할 새 준비의 승인
4. 실제 prefix 생성·suffix 전송과 용량 검사

2·3번 각각에서 동시 요청은 `(예측 데드라인, 사용자 ID, 준비 epoch, 목표 서버 ID)` 순으로 처리한다. 한 요청이 거절돼도 들어갈 수 있는 다른 요청은 계속 검사한다. 이 승인 순서는 **모든 새 비교군에 동일하게 적용**한다. 계획 후보 순서나 실제 GPU EDF/FCFS 비교와는 구분한다. 전체 실험에 공통으로 적용되는 메모리 규칙의 효과를 제안만의 이득으로 집계하지 않는다.

## 4. 핵심 알고리즘과 기본 설정

```text
1. 실제 전환·취소·세션 변경을 처리한다.
2. 유효한 계획은 유지하고 새 후보를 목표 MEC 서버별로 모은다.
3. 실행 중 준비와 유지 계획으로 예상 GPU 점유를 구성한다.
4. 새 후보를 예측 전환 시각 순으로 방문한다.
5. 각 준비 창에서 prefix 소요시간과 suffix 잔여 지연을 추정한다.
6. 중단·조기 노출·외부효과 대용치의 비용이 최소인 창을 선택한다.
7. 선택한 구간을 계획에 반영하고 다음 후보를 평가한다.
8. 실제 생성량을 확인하고 기존 준비의 예약을 갱신한 뒤, 새 시작을 승인하거나 보류한다.
9. 예약 범위에서 EDF prefix 실행과 링크 분배를 진행한다.
10. 다음 전환 시 미완료 부분을 복구하고 소비한 준비 예약을 반환한다.
```

비용은 기존 `α × 예상 SIT + (1−α) × 조기 노출 + β × 외부효과 대용치`를 유지한다. 메모리 부족의 영향을 숨기기 위한 가중치 재조정은 이번 구현과 함께 하지 않는다.

| 설정 | 주 비교 기본값 |
|---|---|
| α / β | 0.8 / 1.0 |
| 최대 준비 창 / 창 격자 | 5초 / 0.2초 |
| 제어 간격 | 0.5초, 이후 0.25초 민감도 |
| suffix 수요 기준 | 링크 용량의 60%, GPU 동시성으로 링크 경합 근사 |
| 예측 신뢰도 문턱 | 0(비활성) |
| 핵심 방식의 detour | 끔. 불일치 시 반응형 하이브리드 복구 |
| 보조 detour 설정 | 별도 실험에서만 켬; 홉 한도 2, 정착 유예 10초 |
| 메모리 예산 | 준비용 서버당 기존 기본값 6000 MB, 전 정책 동일 |

공통 메모리 규칙은 GPU/백홀 공동 최적화나 기존 슬롯의 전면 재계획을 새로 도입하지 않는다. 개별 계획을 유지하는 기존 탐욕 구조를 사용한다. GPU 점유에서 구하는 링크 경합 대용치의 한계도 명시한다.

## 5. 비교군과 주장 범위

네 개의 요약 막대만으로 시작 시점의 효과를 분리하지 않는다. [기존 평가 설계 §6](coordination_algorithm.md#6-기존-ablation을-그대로-timing-only라고-부르면-안-되는-이유)의 사다리를 유지한다.

- P0: 기존 복구 의미를 유지한 Pallas 근사 + 공통 메모리 규칙
- P1: P0의 잔여 복구만 조율형과 통일
- E: P1의 시작을 일정 시간 앞당김. 당김 폭은 결과를 보기 전에 고정하고 동일 최대 창 적용
- T0→T4: 계획 유지 → 예상 점유 → 외부효과 → suffix 방식 → EDF 실행을 단계별 추가
- T5: T4에 detour를 추가한 별도 보조 실험

기존 사다리 명칭 T0/T1 등의 상세 매핑은 연결 문서의 표를 따른다. T4가 새 핵심 제안이다. 누적 추가와 Full에서 한 요소만 끄는 비교를 함께 설계한다. 예측 잡음에서만 동작하는 보조 기능을 기본 조건의 이득으로 설명하지 않는다.

논문에 사용할 정의:

> 예측된 이동 데드라인과 예상 GPU 점유를 이용해 복수 세션의 KV 준비 시작 시점을 선택하는 탐욕형 조율 방식. 준비용 메모리는 공통 예약 규칙으로 제한하고, 전환 후 잔여 복구를 포함해 평균 및 꼬리 지연을 평가한다.

이 문장은 **예약 버전**의 방법 정의에 사용한다. 기존 결과에는 적용하지 않는다. 다음 표현은 주장 범위에 포함하지 않는다: 전환 전 완료 보장, 전역 최적성, 최악 사용자 보장, 모든 GPU 메모리의 용량 준수, 시간별 백홀의 정확한 공동 예약. 기존 7–8% 격차는 조건을 통일한 재검증 전까지 보류한다.

## 6. 2일차 구현 인계와 완료 기준

공통 예약 관리자는 정책별로 중복 작성하지 않는다. 예약표를 생성·승인·확대·반환하는 경로와 실제 자원 진행 직전의 검사를 연결한다.

| 위치 | 다음 구현 항목 |
|---|---|
| `environment.py` 또는 별도 메모리 모듈 | 서버별 예약 합계, 소유자별 예약량, 원자적 승인·확대·반환, 실제 점유 검사 |
| `policies.py` | Pallas·조율형 시작/취소 경로 연결, detour 정착 및 복제본의 예약 식별 |
| `run.py`, `minisim.py` | 세션 변경·전환·자원 진행·종료 시 처리, 같은 규칙과 실행 순서 |
| `metrics.py` | 예약/실사용 첨두, 미사용 예약 적분량, 시작 보류·확대 거절·메모리 취소·예산 초과 기록 |
| 테스트 | 아래 경계 사례와 소규모 실행에서의 보존 조건 |

Turn-boundary는 별도 `BoundaryJob` 경로를 사용한다. 이번 주 핵심 비교에는 포함하지 않으며, 예약 모델로 대안을 다시 비교할 때는 이 경로까지 연결한 후 실행해야 한다. 미지원 경로는 새 예약 모드에서 조용히 우회하지 않고 명시적으로 거절한다. 활성 정착 준비는 지원할 때 GPU 점유 계획에도 포함한다.

2일차의 통과 조건:

- [x] 같은 주기에 여러 준비를 승인해도 예약 합계가 예산을 넘지 않음
- [x] 예측 지연·예상보다 큰 토큰 증가에서 초과 쓰기 전에 확대 승인/취소
- [x] suffix 전송/지연 복구 두 모드 모두 같은 예약 규칙 적용
- [x] prefix 완료만으로 예약을 조기 반환하지 않음
- [x] 완료·취소·목표 변경·영역 재진입·실험 종료·복제본 취소의 반환 누락 없음
- [x] 중복 반환에도 음수 예약이나 이중 반환 없음
- [x] 예산 0, 요청량=예산, 요청량>예산의 동작 확인
- [x] Pallas와 핵심 조율형에 같은 요청을 주면 승인 결과가 같음
- [x] 준비 상태가 있으면 예약 소유자가 존재하며 실제 점유 ≤ 예약량 ≤ 서버 예산
- [x] 보류 시도 수와 연속 보류 요청 구간 수를 구분하고 취소량은 실제 생성분만 계산

예약 전 결과는 기존 버전으로 유지하고, 새 실행에는 알고리즘·메모리 모드·설정·코드 해시를 기록한다. 기본 실행 동작을 전환하기 전에 회귀 확인을 거치며 새 결과 파일명을 사용한다. 구현 전부터 ‘메모리 초과 0건’이나 개선율을 보고하지 않는다.

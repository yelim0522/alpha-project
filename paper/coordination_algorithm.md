# 조율 알고리즘 명세와 최종 평가 설계

2026-09-21 · 현재 구현 기준 명세 v1. 이 문서는 새 정책을 구현했다는 뜻이 아니라, `sim/policies.py`의 `Coordinated`를 논문에 정확히 기술하기 위한 기준이다. 분석 기준은 커밋 `f7e3deb`이며 이번 작업에서는 정책·시뮬레이터의 동작을 바꾸지 않았다.

## 1. 한 문장 정의

**같은 목표 서버로 이동할 사용자들을 예측 전환 시각 순으로 살펴보고, 이미 실행·계획된 준비의 GPU 점유를 고려해 각 사용자의 준비 시작 시점과 후속 토큰 처리 방식을 선택하는 탐욕 계획기.**

시작 시점 조율이 핵심이고 EDF 실행 순서·후속 토큰 처리·잔여 복구·임시 원격 전달은 구분되는 구성 요소다. 모든 작업을 겹치지 않게 직렬화하지 않는다. 배칭 용량 안의 동시 준비는 허용한다. Reactive/Pallas/Coordinated를 자동 선택하는 시스템은 아니다.

## 2. 입력·출력·상태

| 항목 | 현재 코드의 의미 |
|---|---|
| 사용자 입력 | 목표 서버 예측, 예측 전환 시각, 현재 문맥 토큰 수, 현재 상태 보유 서버와 무선 접속 서버 |
| 자원 입력 | 요청당 prefill 속도, 서버 배칭 배수, 백홀 용량, 준비용 메모리 예산 |
| 유지 상태 | 실행 중 준비와 사용자별 기존 계획(`target`, `t_ho`, `start`, `tw`, `dur`, `stream`) |
| 계획 출력 | 준비 창 길이 `tw`, 시작 시각 `t_ho − tw`, suffix를 전송할지 나중에 복구할지 |
| 실행 출력 | 준비 시작/보류, GPU 실행 순서, 전환 시 잔여 복구 또는 임시 원격 전달 |

기본값: 비용 가중치 α=0.8, 외부효과 가중치 β=1, 최대 준비 창 5초, 후보 창 격자 0.2초, 링크 여유 기준 ρ=0.6, 원격 전달 홉 한도 2, 정착 유예 10초. 예측 신뢰도 문턱은 기본 0으로 비활성이다. 후보 창 격자와 시뮬레이션 제어 간격(기본 0.5초)은 별개다.

## 3. 논문용 의사코드: 10줄

```text
입력: 현재 시각 t, 사용자별 전환 예측, 실행 중 준비, 기존 계획, 서버 자원
 1. 실행 중 준비의 목표가 바뀌면 취소하고, 같은 목표면 데드라인을 갱신한다.
 2. 충분히 머문 원격 전달 사용자는 메모리 검사를 거쳐 현재 접속 서버로 배경 준비한다.
 3. 유효한 기존 계획은 유지하고, 새로 계획할 사용자를 목표 서버별로 묶는다.
 4. 각 목표 서버에서 실행 중 prefix와 유지 계획으로 예상 GPU 점유 구간을 만든다.
 5. 새 후보를 예측 전환 시각 오름차순으로 방문한다.
 6. 각 준비 창 w에 대해 prefix 완료 시간·경합 대용치·suffix 처리 비용을 추정한다.
 7. 중단·조기 준비·외부효과 비용 J(w)가 최소인 창을 선택하고 점유 구간에 추가한다.
 8. 시작 시각이 다음 제어 주기 안인 계획은 현재 준비 메모리 검사를 통과하면 시작한다.
 9. 실행기는 EDF 순으로 prefix를 처리하고 백로그가 있는 suffix 전송끼리 링크를 분배한다.
10. 실제 전환 때 준비가 맞으면 잔여 복구, 아니면 조건에 따라 원격 전달/반응형 복구한다.
```

`run.py`의 실제 루프는 이번 주기에 감지한 전환을 **먼저** 처리하고(이전 주기 예측 사용), 새 예측으로 계획한 뒤 자원을 진행한다. 10행은 이 전환 처리 규칙을 나타낸 것이며 1–9행 이후에만 전환을 검사한다는 뜻이 아니다.

## 4. 비용 함수와 자원 제약의 정확한 범위

후보 i의 현재 문맥을 Kᵢ, 전환까지 남은 시간을 Rᵢ, 준비 창을 w라 하면 예상 prefix 길이는 `Lᵢ(w) = Kᵢ + r_d(Rᵢ − w)`다. 계획기는 예상 prefill 소요시간 Dᵢ(w), suffix 잔여 지연 Qᵢ(w), 외부효과 대용치 Eᵢ(w)를 구해 다음을 최소화한다.

$$
J_i(w)=\alpha\left[T_0^p+\max\{0,D_i(w)-w,Q_i(w)\}\right]
 +(1-\alpha)\max\{0,w-D_i(w)\}+\beta E_i(w).
$$

후보 창은 `0, g, 2g, …, min(5초, Rᵢ)`이며 끝점도 포함한다. 비용이 같으면 먼저 평가한 작은 창을 유지한다. 시작 시각은 `예측 전환 시각 − w`; 점유 시작 격자는 내림으로 근사한다. 따라서 제어 간격·계획 격자에 따른 오차가 있다.

- **하드 데드라인 아님:** `finish ≤ handoff`를 강제하지 않는다. 기한을 넘긴 잔여 작업을 비용에 포함하며 준비가 불가능해도 가장 싼 창을 선택한다. 불확실성 분포를 적분한 ‘기대 지연’이 아니라 점 예측 아래의 비용 추정이다.
- **GPU:** EDF 추정 속도는 `v × min(1, max(0, P − n_early))`다. 실행 중 준비 및 기존 계획을 근사한 프로파일 위에서 계산한다. 새 후보를 넣은 뒤 이전 후보들의 완료 시각을 모두 다시 계산하지는 않는다. 실행기는 별도로 서버당 `P × v`와 요청당 `v`를 제한한다.
- **외부효과:** EDF에서 후보가 처리될 수 있고 더 늦은 데드라인 작업을 포화 구간에서 밀어내면 그 구간 길이를 누적한다. 모든 타 사용자 완료 지연을 다시 계산한 정확한 사회적 비용이 아니다. 같은 시점에 새 후보를 EDF 순으로만 넣으면 앞서 배치한 후보는 모두 이르거나 같은 데드라인이므로 이 항이 0일 수 있다. 나중 데드라인의 유지 계획 등이 있어야 EDF 외부효과가 생긴다. FCFS 변형에서는 포화 구간 누적으로 다르게 근사한다.
- **백홀:** 독립적인 시간별 링크 예약표를 만들지 않는다. GPU 프로파일에서 얻은 최대 동시성 k를 써서 `B/k`로 근사한다. `k × r_d × c > ρB`이거나 지연 복구가 더 싸면 suffix를 미룬다. k는 실제 스트림 수와 다를 수 있다. 실제 준비 전송은 백로그가 있는 스트림끼리 나눈다.
- **VRAM:** 시작 시 `현재 만들어진 준비 바이트 + 새 사용자 현재 문맥 바이트 ≤ 예산`을 검사한다. 계획 지평의 예약이나 전체 상주 메모리 제약이 아니다. 특히 새로 시작한 준비는 아직 생성된 prefix가 0이므로 같은 주기의 여러 준비가 각각 승인을 받을 수 있다. 이후 생성량이 예산을 넘는 작은 사례가 재현됐다. **현재 검사를 미래 메모리 용량 보장으로 쓰면 안 된다.**
- **실제 실행과의 차이:** 활성화 직렬화는 실행 시 계산하지만 창 선택 비용에는 같은 주기의 활성화 수가 직접 들어가지 않는다. FCFS 계획 추정은 균등 분배인 반면 실행은 트리거 순 예산 할당이다. 정착용 배경 준비는 실행 자원은 쓰지만 일반 활성 점유 목록에서 빠지는 경로가 있다. 이들은 근사 오차이며 정확한 자원 예약 알고리즘이 아니다.

따라서 제안받은 `expected interruption + λ × contention`, GPU/BW/VRAM의 모든 시각 하드 제약 문제를 **이미 구현했다고 쓰지 않는다.** 현재 알고리즘은 중단·조기 준비 비용에 외부효과 대용치를 더하는 점유 기반 휴리스틱이다.

## 5. 코드 대응과 유지 규칙

| 코드 | 역할 / 주의점 |
|---|---|
| `Coordinated.on_step` | 예측별 분류, 계획 유지·폐기, 메모리 검사와 실제 시작 |
| `Coordinated._plan_target` | 목표 서버별 점유 구성 → 새 후보 EDF 순 방문 → 창 탐색 |
| `Coordinated._fluid_prefill` | prefix 소요시간·외부효과 대용치·최대 동시성 계산 |
| `Coordinated._cost_k` | 창별 비용과 suffix 방식 결정 |
| `Coordinated.plan_handover` | 잔여 prefix/suffix 분할 복구 또는 조건부 원격 전달 |
| `advance_preparations` | 실제 준비 GPU 예산 할당과 링크 분배 |
| `run_policy` | 무선 전환 처리, 활성화 직렬화, 대화 시계, 정착 완료 |

계획은 매번 전부 다시 최적화하지 않는다. 목표 서버가 같고 예측 시각 변화가 `max(창 격자, 제어 간격)` 이하면 이전 계획을 유지한다. 큰 변화는 재계획한다. 진행 중 준비는 목표가 같으면 데드라인만 갱신한다. 메모리 부족으로 시작을 보류해도 계획은 남는다.

`Pallas로 환원`도 조건부다. 점유가 없고 관측 유효율이 명목 용량과 같은 새 상태에서는 창별 비용이 일치한다. 그러나 과거 혼잡이 EWMA에 남거나, 유지 계획이 있거나, 전환 시 잔여 suffix 복구가 필요하면 정책 전체가 항상 동일하지는 않다. Pallas 근사는 잔여 suffix 분할을 허용하지 않고 Coordinated는 허용한다.

단순 `O(NGH)`는 프로파일 재구성 비용을 생략한다. 현재 구현은 새 후보 N, 시작 시 기존 구간 I, 프로파일 격자 H, 후보 창 G, 유체 탐색 최대 반복 F에 대해 대략 `O(N log N + N(I+N)H + NGF)`의 상한으로 설명할 수 있다. F는 긴 prefix 때문에 H를 넘을 수 있다. 실용성은 제어 주기당 실측 실행시간으로 별도 평가해야 한다.

## 6. 기존 ablation을 그대로 timing-only라고 부르면 안 되는 이유

기존 사다리는 `planned-k → +social → +suffix → +EDF → +detour`다. 첫 단계부터 계획 점유, 계획 유지, 링크 유효율 근사, Pallas와 다른 잔여 분할 복구가 함께 들어간다. 따라서 Pallas와 첫 단계의 차이를 준비 시점 하나의 효과라고 해석할 수 없다. `suffix_mode=False`도 전환 시 잔여 분할 복구를 끄지 않는다.

최종 비교는 아래 순서로 같은 이동·작업 표본·자원 설정에서 실시한다. **아래는 설계이며 이번에 결과를 새로 생산하지 않았다.**

| 단계 | 바꾸는 요소 | 상태 |
|---|---|---|
| P0 | 기존 Pallas 근사 | 구현됨; 원 비교군 유지 |
| P1 | Pallas에 제안과 같은 잔여 복구만 적용 | 별도 변형 필요; 복구 메커니즘 효과 분리 |
| E | P1에서 고정된 양만 일찍 시작 | 별도 변형 필요; ‘그냥 일찍 시작’ 통제, 사전 정의한 당김 폭 스윕 |
| T0 | 관측 유효율로 창 선택하되 계획을 유지 | 기존 `Coordinated(planned_k=False, social=False, suffix_mode=False, edf=False, detour=False)`로 구성 가능; P1과 복구를 맞춘 뒤 비교 |
| T1 | T0에 계획 점유 적용 | 기존 `abl-planned-k`; timing-only가 아니라 점유 인지 단계 |
| T2 | T1에 외부효과 추가 | 기존 `abl-+social` |
| T3 | T2에 suffix 전송/지연 복구 선택 | 기존 `abl-+suffix` |
| T4 | T3에 EDF 실행 순서 | 기존 `abl-+edf` |
| T5 | T4에 원격 전달 폴백 | 기존 `coordinated` / `abl-+detour` |

누적 사다리만으로는 상호작용이 가려진다. Full에서 각 요소를 하나씩 끄는 비교도 병행하고, 원격 전달은 예측 잡음 조건에서 따로 확인한다. 기존 192명 표에서 suffix 추가가 평균·p99를 약간 악화시킨 사실도 유지한다. 모든 구성 요소가 모든 지표를 개선한다고 주장하지 않는다.

측정은 SIT 평균/p99, 응답별 대기·추가 완료 시간, 완료·미완료 응답, 동시 스트림 첨두, 전송량·낭비·ITL을 함께 한다. 원인 확인용으로 계획 시작 시각과 실제 시작 시각, 예상/실제 prefix 완료 시각, 외부효과 항이 양수인 빈도, 메모리 승인 보류·예산 초과, 계획기 실행시간을 추가로 기록해야 한다. 이 기록은 아직 구현되지 않았다.

## 7. 기존 ‘최적해 대비 7–8%’는 보류

`sim/optgap.py`의 비교는 현재 다음 이유로 전체 제안의 정식 optimality gap이 아니다.

1. K=5에서는 전수 탐색에 `max(grid, 0.5)`를 사용하지만 온라인 정책에는 계속 `grid`(기본 0.25)를 넘긴다.
2. 전수 탐색은 항상 suffix 전송을 사용하고 제안은 suffix 모드를 선택할 수 있다. 온라인 정책의 후보 끝점·제어 주기별 재계획에 따른 선택 시각도 탐색 가능한 시각 집합과 자동으로 같아지지 않는다.
3. `FixedSchedule`은 시작 시 VRAM 검사를 우회한다. 기본 예산이 넉넉해도 제약이 동일하다는 구현 보장은 없다.
4. 전수 탐색 목적은 `Σ(0.8 SIT + 0.2 조기 노출)`이고, 탐욕 계획의 국소 외부효과 항 자체의 전역 최적값을 구하는 것은 아니다.
5. 기존 원고의 인스턴스 10개 수치에 대응하는 시드별 결과·설정 기록이 저장되어 있지 않다. 이번에는 해당 수치를 재현하지 않았다.

다음 검증은 우선 **시작 시점만의 제한된 문제**로 고정한다. 양쪽의 후보 시작 시각·실행 시각·suffix 방식·잔여 복구·GPU 순서·메모리 처리·목적함수를 같게 맞추고, 온라인이 선택한 스케줄이 탐색 공간 안에 있는지 검사한다. 개별 인스턴스·최적 스케줄·실제 트리거·목적값을 저장한 후 격차를 계산한다. 그때도 작은 이산 문제의 경험적 격차이지 큰 환경의 근사비 보장은 아니다.
